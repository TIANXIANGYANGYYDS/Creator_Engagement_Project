## 从真实响应定位的实现问题

### 1. 已经返回的回复正文被丢弃，剩余回复也没有继续获取

原始数据索引 5538 对应笔记 `6aca09f1000000000202a5c7`：

- 原互动 SSR 给出总评论数 28。
- `/api/sns/web/v2/comment/page` 给出 9 条主评论，每条还带一条 `sub_comments`，合计 9 条回复正文。
- 旧解析器只遍历最外层 `comments`，把上述 9 条已经收到的正文丢弃。
- 两条主评论仍有后续回复，按官方前端的 `root_comment_id + sub_comment_cursor` 调用 `/api/sns/web/v2/comment/sub/page`，实际再取得 5、3、2 条，共 10 条回复。
- 合计 **9 条主评论 + 19 条回复 = 28 条正文**，均有唯一评论 ID，与当前总数核对一致。

实现现在保留内嵌回复，并逐页追加剩余回复，按评论 ID 去重；楼中楼增加 `parent_comment_id`。遇到限制、重复游标、缺失分页标记或回复笔记归属不匹配，保留已经取得的正文并将 `comments_complete` 标为 false。该标记贯穿服务模型到批量接口的 `complete`，不会仅因主评论已到末页就声称回复全部完成。

### 2. 互动缺失导致组合采集连评论也不取

`fetch()` 同时请求互动与评论时，目标笔记存在但计数为空会提前返回。现在仅单独请求互动时返回“计数不可用”；组合采集继续尝试评论。空字段仍为 null，不捏造点赞、收藏、分享数。

详情 SSR 请求此前没有主动带入已授权的小红书会话，现在携带同一存储会话。此次两条空值样本在带账号的 SSR 中仍为空，因此不将这个调整描述为已补回互动数值。

### 3. HTTP 461 的原始限制原因可能被签名重试覆盖

旧 `_get()` 对所有 `PlatformCrawlerError` 都切换签名再请求。200 条测试中，第一次 461 触发本地保护，第二次被本地保护拒绝后，错误最终变成泛化的 `engagement request failed`。

现在只有已知签名格式拒绝 HTTP 406 才切换格式；HTTP 461/429 等原始错误直接保留，外层也不再自动重试。明确的会话和账号业务拒绝分别分类，不将它们伪装成有效空评论。

前端源码显示，461/471 的处理还参考验证头、业务码和策略字段。上轮未保留完整正文，不能断言那次一定是 IP 封禁或一定有可用数据。本轮对相同笔记 `6ac993a5000000001203897e` 的复核在修复前就已返回 HTTP 200、有效空末页，未复现 461。因此不能将恢复归功于本轮代码修改，也没有据此放宽对 461 的成功判定。

### 4. 作者查找失败被互动与评论重复执行

同一无访问 token 的 URL，两个操作会分别查作者最多 20 页。现在对“查满 20 页仍未找到”与“作者列表结束未找到”的结果暂存 120 秒，避免紧接着重复查找；认证、网络错误和签名错误不存入这个缓存，到期后允许重新查找。

### 5. 原限速在操作入口，内部翻页仍可能连续请求

新增 `XIAOHONGSHU_REQUEST_INTERVAL_SECONDS`，默认 5 秒，在共享 HTTP 客户端逐次执行，覆盖作者翻页、互动、主评论与回复分页，并序列化这些直连请求。本轮独立服务验收临时设为 8 秒，实际 12 次请求的最短“前次完成到下次开始”间隔为 8.0004 秒，代理取号为 0。

这是降低请求密度的措施，不能保证平台不会再次触发验证。200 条低速批次未在本轮恢复执行。

## 互动字段的核查结果

两条样本 `6ac993a5000000001203897e`、`6aca578d000000001c01e62a`：目标 ID 与正文能核对，已登录浏览器运行时和带账号的 SSR 中，likedCount、collectedCount、shareCount、commentCount 仍是空字符串。评论接口独立请求成功，返回有效空末页。

前端在部分计数运算中存在空值转零的逻辑，但单靠该逻辑不能证明任意空字符串都是真实的零。本次保留未知值，没有把“请求到笔记”或“评论为空”包装成取得了全部互动数值。

还发现 SSR `comments` 是默认初始状态：`list=[]、hasMore=true、firstRequestFinish=false`。因此不能把初始空列表或页面占位提示当成评论总数为零的依据；有 28 条评论的正对照初始状态也是这种结构。有效空页必须由真实评论 API 的列表和分页标记核验。
