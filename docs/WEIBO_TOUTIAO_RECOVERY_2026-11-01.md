# 微博连接恢复与头条评论恢复

日期：2026-11-01。状态：工作区修改、隔离验证通过，未提交、未部署、未重启线上。保留此前代理池优化；本轮实网验证仍关闭 `PROXY_LEASE_OPTIMIZATION_ENABLED`，单任务串行，不向线上提交采集任务。

## 证据与修改

### 微博

真实失败发生在访客初始化请求：一次 5 秒超时，libcurl `CONNECT_TIME=0`、`HTTP_CONNECTCODE=0`；另一次代理 CONNECT 已返回 200，但 TLS 尚未建立即失败。它们是连接阶段故障，不能据此判断微博业务接口慢或 TLS 指纹被识别。

`required` 代理模式下，正常协议尝试耗尽后，只有明确的传输故障才额外恢复，最多 2 次，每次沿现有租约流程重新选出口并重新执行访客链路。额外尝试必须在本次协议操作开始后的 25 秒内结束；正常尝试原有的超时配置不变。以当前正常 3 次为例，最多 5 次。登录、数据校验、内容不可见等错误不获得这两次额度。

这增加了对连续坏出口的容忍度，但不会让不可连接的代理恢复可用。隔离故障注入后的实网测试仍遇到“3 次注入超时 + 2 个真实坏出口”而失败，已经保留证据；不能把小样本成功解释成故障清零。出口质量仍需在后续代理池优化中处理。

### 头条

- 正常协议尝试耗尽后，传输错误或明确限流/访问限制可额外换出口重试最多 2 次，沿用上述 25 秒恢复窗口。当前正常额度为 1 次，因此最多 3 次；登录失效和无效业务数据不会扩大重试。
- 普通文章的浏览器兜底改为复用 `BrowserPageContext`，在浏览器当前会话内主动读取指定评论页，并校验 `group_id`、作者信息、评论和游标。浏览器不再点击泛化的“评论”按钮，避免把发表评论/登录控件当成读取评论入口。
- 浏览器同源 `fetch` 使用 15 秒 AbortController 超时。头条整个浏览器恢复阶段最多等待 60 秒，达到预算后取消并释放资源；原有浏览器尝试次数上限仍适用。
- 页面显示挑战时仍尝试当前会话的公开评论接口；接口返回可验证数据才成功。如果接口也受阻，则保留 `blocked`，不返回伪造的零评论。
- 第 1 页同时满足“目标文章页具有站点错误页结构并明确提示内容不存在”和“目标评论接口返回无作者、零计数、空列表且无下一页”，才返回不可重试的 `unsupported`。停止页面刷新和多轮浏览器重试。
- 单独的错误页、匿名空 JSON、深页空列表均不足以判定整篇作品不可查。实测发现文章路径报错的作品仍可读取评论，因此不能在请求评论接口前直接结束。

同步 API 的 HTTP 错误契约未调整：内容不可查仍按现有路由返回 502，但原因明确，内部不会继续重试，也不会记为成功的零评论。分析技术失败率时应按业务原因排除，不应把所有 502 一律视为网络故障。

真实浏览器单次探测仍观察到出口网络错误；恢复逻辑不能保证任意一次浏览器调用成功。早期分析脚本的截图等待字体曾产生额外超时，已移除该干扰后重新验证，受该问题影响的耗时不作为最终版本性能证据。
