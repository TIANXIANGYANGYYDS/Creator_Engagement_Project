## 微博 / B 站修复验收

### 原因和修复

- 微博：原失败样本中 7 条实际返回热门流 `ok=0, msg=还没有人评论哦~快来抢沙发！`，页码接口返回 `ok=0, msg=暂无数据`。原代码漏识别前一条消息，错误概括为登录或访问限制。现在只有两个接口都明确无可见评论时才返回空列表；总量来自匹配目标 MID 的详情，未知值仍保留 `null`。这修正了下文初次诊断中尚未确认的业务拒绝原因。
- 微博：实测热门流每页 20 条，页码接口每页 10 条且排序不同。原逻辑在热门流深页受限后切到相同数字的页码接口，产生重叠，且无法证明无遗漏。现在分页游标固定接口，重试也不能换流；后续页受限时保留已获得的一级评论，批量响应 `complete=false`。从首页即使用页码接口时，后续保持该接口。
- B 站视频 `BV1Vnxi6dEts`：官方网页明确显示“当前稿件up主设置为仅自见”，页面初始状态和详情 API 均为 `62012`。现在返回“仅 UP 主自己可见（62012）”，停止协议重试和浏览器兜底，不再让已确认的内容限制消耗 120 秒预算。
- B 站 Opus `1265026696616083496`：页面 HTTP 404/验证码本身不能证明不可见。通过当前代理租约获取匿名 `buvid3/buvid4` 后，官方 Opus 详情 API 与浏览器会话内请求均返回 `4101152, 动态不可见`。新增页面缺失时的官方 API 核验路径，仅该明确业务码停止无效重试；其他网络、未知业务和风控错误保留原有重试与浏览器兜底。
- B 站公开 Opus 的回复接口可能没有总数字段。现在优先使用回复接口明确总数，缺失时使用已核验目标详情中的评论总量；详情明确为零时避免无意义重试。异常结构不能作为空列表成功。视频和 Opus 详情均检查目标标识，一级评论保留回复数量，不展开回复正文。

保持匿名策略、强制代理、原有浏览器兜底和重试次数，没有引入登录、直连或付费识别服务。此次未还原或修改签名算法，验收针对真实请求、业务响应、目标绑定和评论数据。

## 已确认的评论问题

### 抖音：临近过期的代理耗尽两次尝试

5 次失败中，3 次的两轮尝试都报“抖音访客代理即将过期，需更新会话”，对应 6 条代理淘汰记录；另外 2 次先发生评论接口连接超时，随后浏览器建立 HTTPS 连接失败，单次约 31.3 秒。

代码对应关系：

- [代理选择](../app/crawlers/proxy_provider.py)的 `_select_available_slot` 在负载相同时优先选择最早到期的槽位，没有为访客初始化预留最低剩余时长。
- [抖音访客初始化](../app/crawlers/douyin_visitor.py)的 `_bootstrap` 完成浏览器操作后，才检查剩余租约并减去 10 秒；结果不足时整轮失败。
- [协议重试](../app/crawlers/engagement.py)淘汰该 IP 后重新取池中代理，同一批代理可能同时临近过期，第二次尝试仍失败。

离线复现将一个 8 槽位代理池的剩余时间设为 8 秒：两次连续租用都拿到剩余 8 秒的旧代理，两次失败后池中仍有 6 个同龄槽位，没有补充新批次。该复现使用模拟代理，证明调度条件；不把模拟的 8 秒当作历史真实 TTL。

这是明确的租约与初始化预算不匹配。后续修复应在启动访客浏览器前确保足够的代理寿命，并保证刷新后会话绑定新出口；仅增加协议尝试次数会继续消耗同批代理。

### 微博：访客连接失败与评论业务拒绝并存

9 次失败中，7 次至少有一轮明确报“微博热门流和匿名页码接口均要求登录或触发访问限制”，部分又混合网络失败；其余 2 次只见连接失败。原始上游业务码未完整保存在历史日志中，不能进一步断言全部属于登录失效。

当前链路在读取桌面目标详情后，依次尝试 `m.weibo.cn/comments/hotflow` 和 `m.weibo.cn/api/comments/show`。本轮两条原失败样本三次尝试均在 `visitor.passport.weibo.cn/visitor/visitor` 发生超时或 TLS 错误，尚未进入评论接口。

补充回放取得非空结果：一条原成功链接返回 1 条一级评论，一条原失败链接返回 4 条。目标详情 MID 匹配，评论 ID 各自去重一致，业务 `ok=1`、`max_id=0`，回复数均为 0。因此微博是间歇性失败，不能据失败样本认定匿名路径全面不可用，也不能据两条恢复样本宣称已修复。

### B 站：上游业务失败被泛化，重复兜底耗尽同步时限

- 视频 `BV1Vnxi6dEts`：回放两次返回 HTTP 200、业务码 `62012`、无有效详情；第三次连接超时。代码把业务失败归为通用的 `bilibili view payload is unavailable`，最后一次网络失败又覆盖了此前业务原因。本轮没有验证 `62012` 的精确业务含义，不将其等同于删除。
- Opus `1265026696616083496`：协议回放三次均 HTTP 404。历史线上请求还出现缺少初始数据、浏览器要求登录或没有捕获目标数据，最后触发 120 秒同步上限。单凭页面 404 不能确认作品已删除。

协议失败之后仍会进入多次通用浏览器兜底。需要保留上游业务码、区分已确认不可恢复状态和暂时网络失败，再约束无效兜底；当前证据不支持关闭所有 B 站浏览器兜底。
