# 成本、容量与保护策略

验证日期：2026-08-21。本文只描述运行成本和服务保护；每个平台的字段、分页和会话边界见
`PLATFORM_FLOWS.md` 与 `PROTOCOL_MATRIX.md`。

## 请求次数和 IP 次数不是同一口径

外部接口保持业务上清晰的两条：

```text
GET /api/v1/interactions?url=...&media_name=...
GET /api/v1/comments?url=...&media_name=...&page=1
```

两个接口独立执行、独立缓存。只有完全相同的接口参数才会合并并发重复任务，并复用 120 秒
结果；互动量缓存不会冒充评论缓存，评论首页缓存也不会冒充互动量缓存。

一次业务接口内部可能包含页面预热、访客状态初始化和数据接口等多个 HTTP 请求。它们可以
共用一个代理租约，但仍应分别计入上游请求数量。反过来，一个代理 IP 在约 170 秒可用期内
也可以连续承载多次业务请求，所以不能把“一个 IP”直接等同于“一次请求”。

## 八个平台请求关系

| 平台 | 互动量来源 | 评论来源 | 同一个上游响应同时返回两类数据 |
|---|---|---|---|
| 抖音 | `aweme/detail` | `comment/list`，每页一次 | 否；匿名会话另有预热和 `ttwid` 初始化 |
| 今日头条 | 文章 HTML SSR | `tab_comments`，每页一次 | 否 |
| 微信公众号 | 文章 HTML；缺失时 `getappmsgext` | HTML 预载精选评论；缺失时 `appmsg_comment` | 有条件：HTML 恰好同时预载统计和精选评论时是一次，否则分开 |
| 小红书 | `feed` 或笔记 SSR | `comment/page`，每页一次 | 否 |
| 好看视频 | 首页预热后读取目标页 SSR | `comment/get`，每页一次 | 否 |
| 快手 | `visionVideoDetail` | `comment/list`，每页一次 | 否 |
| B站 | 视频 `view` / 直播 `get_info` | 视频 WBI 评论 / 直播最近弹幕 | 否；视频评论还需要导航密钥请求 |
| 微博 | `statuses/show` | `comments/hotflow` 或页码接口 | 否 |

因此当前服务不跨互动量和评论接口做强制合并。公众号是否单响应命中两类数据由文章实际 HTML
决定，不能预先把所有公众号请求都按一次计算。

## 默认保护参数

| 参数 | 默认值 | 作用 |
|---|---:|---|
| `COLLECTION_MAX_CONCURRENCY` | 4 | 全服务最多 4 个上游采集任务 |
| `BROWSER_MAX_CONCURRENCY` | 2 | 最多 2 个 Camoufox；同一平台仍串行 |
| `PROXY_POOL_SIZE` | 2 | 只维护 2 个 51 代理 IP 槽位 |
| `PROXY_MAX_CONCURRENCY` | 2 | 每个 IP 最多 2 个同时在途采集任务 |
| `ENGAGEMENT_CACHE_TTL_SECONDS` | 120 | 相同接口和相同参数的结果复用 2 分钟 |
| `ENGAGEMENT_CACHE_MAX_ENTRIES` | 1000 | LRU 上限，防止缓存无限增长 |

1 GB 左右的低内存服务器应把 `BROWSER_MAX_CONCURRENCY` 设为 1；协议请求仍可保持 4 并发。
不应通过增加 worker 进程绕过这些限制，因为每个进程会拥有独立浏览器槽位、缓存和代理池。

## 51 代理成本

用户给出的价格是 100000 个 IP 共 84 元，因此单个 IP 为：

```text
84 / 100000 = 0.00084 元/IP
```

正确核算公式是：

```text
代理总成本 = 实际新增 IP 数量 × 0.00084 元
平均业务请求成本 = 代理总成本 ÷ 成功业务请求数
平均上游请求成本 = 代理总成本 ÷ 成功上游 HTTP 请求数
直连且没有调用代理池：IP 采购成本 = 0 元
```

例如一个 IP 在有效期内成功完成 100 次上游请求，平均 IP 成本为 0.0000084 元/请求；完成
500 次时为 0.00000168 元/请求。这只是摊销示例，真实数值必须使用代理池的新增 IP 计数和
成功请求计数，不能预先写死为 0.00084 元/次。

51 代理标称有效期 3 分钟，代理池提前 10 秒停止分配，所以每批 IP 可用约 170 秒。默认池
大小为 2；在持续满负载、没有失败淘汰的理论上限下：

```text
每小时 IP = 2 × 3600 / 170 ≈ 42.35
每小时费用 = 42.35 × 0.00084 ≈ 0.0356 元
100000 IP 可连续支撑 ≈ 2361 小时 ≈ 98.4 天
```

代理池不会在无请求时主动刷新，因此低流量的实际消耗更低。若 407 条 URL 连续运行 2–4
小时并启用代理，理论基础消耗约 85–170 个 IP，即 0.071–0.143 元；验证码、代理失败和
平台 5xx 会产生额外淘汰成本。成本主要按“运行时间内实际新增的 IP”增长，不是每个 URL
或每次 HTTP 请求固定扣一个 IP。若整批使用 `direct`，这部分 IP 采购成本为 0。

## 实测负载

测试环境为 `MyAgent` / Python 3.13.12，直连单进程，数值包含 Python 进程自身：

| 平台/诊断路径 | 总用时 | 峰值 RSS | 说明 |
|---|---:|---:|---|
| 抖音互动量和评论联合诊断 | 1.93 秒 | 64680 KB（约 63 MB） | 包含预热、访客初始化、详情和评论等多个 HTTP 请求，不代表一次请求 |
| 快手互动量和评论联合诊断 | 20.17 秒 | 411096 KB（约 401 MB） | 包含页面导航、详情和评论请求，不代表一次请求 |

因此浏览器是内存主耗。默认 2 个浏览器按本次样例估算约 0.8 GB 峰值，再加 API 进程和系统
余量；低内存机器设为 1 后，浏览器部分约 0.4 GB。抖音现已转为协议路径，正常情况下不会
再占用浏览器槽位。当前缓存只复用相同接口和相同参数，不跨互动量/评论接口减少请求数。

## 仍存在的数据缺口

- 公众号：作者关闭评论时不存在可采集内容；任意文章的阅读/点赞和未预载精选评论依赖手机
  微信文章短时会话。服务器仅凭 URL 和 IP 不能替代这个权限。自有公众号可另接官方统计
  API，第三方文章只能使用调用方自己的本地微信会话快照。
- 小红书：公开笔记互动量和评论首屏可游客获取；后续页需要调用方自己的有效 Cookie 与
  URL 对应 `xsec_token`。IP 池不能替代账号会话。
- 微博：匿名接口前两页已覆盖，深页可能返回 `ok=-100`；项目会复用本地登录 Profile 的
  Cookie、XSRF 和 `max_id_type`，有会话时继续热门流分页。
- 快手：当前 API 返回一级评论及每条的子回复数量；子回复有单独 `comment/sublist` 协议，
  但把它混入“每页 20 条一级评论”会破坏现有页码语义，因此未伪装成同一评论页。
- B 站直播：公开接口只能读取最近弹幕窗口，URL 无法回溯已经过去的历史弹幕。若业务需要
  未来全量，需增加常驻 WebSocket 录制器和数据库，而不是对历史 URL 重试。
- 头条、好看：没有在页面公开的收藏/分享等数字保持 `null`；不从推荐流或模糊文案猜值。

这些缺口不是增加 IP 或并发就能解决。当前策略是先返回所有可验证字段，再用
`coverage/reason` 明确指出权限、时间窗口或公开字段边界，避免把空数据当成功。
