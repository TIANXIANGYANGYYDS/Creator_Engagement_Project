# 成本、容量与保护策略

验证日期：2026-08-22。本文只描述运行成本和服务保护；每个平台的字段、分页和会话边界见
`PLATFORM_FLOWS.md` 与 `PROTOCOL_MATRIX.md`。

## 请求次数和 IP 次数不是同一口径

外部接口保持业务上清晰的两条：

```text
GET /api/v1/interactions?url=...&media_name=...
GET /api/v1/comments?url=...&media_name=...&page=1
```

两个接口独立执行、独立缓存。只有完全相同的接口参数才会合并并发重复任务，并复用 120 秒
结果；互动量缓存不会冒充评论缓存，评论首页缓存也不会冒充互动量缓存。

一次业务接口内部可能包含页面预热、访客状态初始化和数据接口等多个 HTTP 请求。它们可以
共用一个代理租约，但仍应分别计入上游请求数量。反过来，一个代理 IP 在约 170 秒可用期内
也可以连续承载多次业务请求，所以不能把“一个 IP”直接等同于“一次请求”。

## 16 项独立实测

`ceil(max(直连实测, 代理实测) × 1.25)`，至少 1 秒。它是容量规划值，不是超时承诺。

## 默认保护参数

| 参数 | 默认值 | 作用 |
|---|---:|---|
| `COLLECTION_MAX_CONCURRENCY` | 4 | 全服务最多 4 个上游采集任务 |
| `BROWSER_MAX_CONCURRENCY` | 1 | 最多 1 个 Camoufox；避免低内存服务器因双浏览器峰值被打满 |
| `PROXY_POOL_SIZE` | 1 | 默认只维护 1 个 51 代理 IP 槽位，优先复用有效 IP |
| `PROXY_MAX_CONCURRENCY` | 2 | 每个 IP 最多 2 个同时在途采集任务 |
| `ENGAGEMENT_CACHE_TTL_SECONDS` | 120 | 相同接口和相同参数的结果复用 2 分钟 |
| `ENGAGEMENT_CACHE_MAX_ENTRIES` | 1000 | LRU 上限，防止缓存无限增长 |

协议请求仍可保持 4 并发。只有确认服务器可用内存充足并完成压力测试后，才把浏览器并发调
到 2；不应通过增加 worker 进程绕过限制，因为每个进程会拥有独立浏览器槽位、缓存和代理池。

## 51 代理成本

用户给出的价格是 100000 个 IP 共 84 元，因此单个 IP 为：

```text
84 / 100000 = 0.00084 元/IP
```

正确核算公式是：

```text
代理总成本 = 实际新增 IP 数量 × 0.00084 元
平均业务请求成本 = 代理总成本 ÷ 成功业务请求数
平均上游请求成本 = 代理总成本 ÷ 成功上游 HTTP 请求数
直连且没有调用代理池：IP 采购成本 = 0 元
```

### 本轮代理实际消耗

上述 16 个独立业务接口以单 IP、单并发连续执行，实际结果为：

```text
总用时                 94.651 秒
业务接口调用           16 次
取得有效结果           14 次（小红书两项未取到）
代理租约               19 次
代理池 API             1 次
实际新增 IP            1 个
失败淘汰/过期换 IP      0 个
实际 IP 成本            1 × 0.00084 = 0.00084 元
按全部调用摊销          0.00084 / 16 = 0.0000525 元/次
按有效结果摊销          0.00084 / 14 = 0.00006 元/次
```

这不是固定单价。该 IP 恰好在 94.651 秒内承载了 19 次租约且未失效；改变调用顺序、平台
风控、代理质量或运行时长后，摊销会变化。直连轮没有调用代理池，实际 IP 采购成本为 0 元。

51 代理标称有效期 3 分钟，代理池提前 10 秒停止分配，所以每批 IP 可用约 170 秒。默认池
大小为 1；在持续满负载、没有失败淘汰的理论上限下：

```text
每小时 IP = 1 × 3600 / 170 ≈ 21.18
每小时费用 = 21.18 × 0.00084 ≈ 0.0178 元
100000 IP 可连续支撑 ≈ 4722 小时 ≈ 196.8 天
```

代理池不会在无请求时主动刷新，因此低流量的实际消耗更低。按已读取的 407 URL 文件平台
分布，并把每个 URL 的互动量和评论各请求一次，以本轮各平台代理实测时间线性估算：

```text
共 814 个业务接口调用
实测速度线性估算        约 79.1 分钟
按 25% 余量规划         约 107.3 分钟
无失败时预计新增 IP      约 28–38 个
预计 IP 成本             0.02352–0.03192 元
```

这是上一轮根据 407 条文件做的线性预测。随后已经完成更大的真实全量，以下实账取代该预测
作为当前容量基线。

### 902 URL / 1804 接口调用实账

两份工作簿合并为 902 个唯一 URL，互动量和评论第 1 页各调用一次。业务缓存关闭，协议
worker 最多 2、单 IP 最多 2 个租约、浏览器并发 1。抖音、头条、B站、微博使用直连；快手
直连出口风控后才启用代理池，并在 IP 变化时重建可丢弃的游客状态。

```text
独立业务接口调用       1804 次
采集器活跃时间         约 130 分钟
含中途诊断的墙钟时间   约 151 分钟
实际新增代理 IP        45 个
实际代理成本           45 × 0.00084 = 0.0378 元
按全部调用摊销         约 0.00002095 元/次
返回互动字段           586 / 902
返回评论正文           601 / 902，共 2820 行
同一 URL 两项都成功    571 / 902
```

45 个 IP 中 42 个记录在正常结束的代理池统计文件，另 3 个来自早期中断阶段的代理获取日志。
这不是“一次请求一个 IP”：最终 648 次快手补测阶段使用 34 个 IP，产生 942 次代理租约，
最大同时在途为 2；其中 29 个按 170 秒到期轮换，4 个因失败提前淘汰。

为定位小红书代理、GeoIP 和缺依赖问题，研发阶段另外取得 29 个 IP，成本 0.02436 元；加上
目录正式测试，本次任务从开始到结束总计 74 个 IP、成本 0.06216 元。研发诊断包含主动运行
的错误策略和启动前失败，不能分摊成生产接口单价；生产基线仍使用上面的 45 个 IP 实账。

按这次最差数据混合和当前单浏览器保护参数机械外推，1 万个 URL（2 万个业务接口）约需
`130 × 10000 / 902 ≈ 1441 分钟`，代理约 `45 × 10000 / 902 ≈ 499 个`，IP 成本约
0.419 元。该值包含大量已经失效或受风控的快手旧 URL；新鲜内容、缓存命中和纯协议比例
提高后会更快，不能把线性值当 SLA。

## 实测负载

测试环境为 `MyAgent` / Python 3.13.12，直连单进程，数值包含 Python 进程自身：

| 平台/诊断路径 | 总用时 | 峰值 RSS | 说明 |
|---|---:|---:|---|
| 抖音互动量和评论联合诊断 | 1.93 秒 | 64680 KB（约 63 MB） | 包含预热、访客初始化、详情和评论等多个 HTTP 请求，不代表一次请求 |
| 快手互动量和评论联合诊断 | 20.17 秒 | 411096 KB（约 401 MB） | 两个独立接口及多个数据请求，不代表一次请求 |

因此浏览器是内存主耗。当前默认收紧为 1 个浏览器，实测浏览器部分约 0.4 GB；若配置成 2，
仅浏览器就可能接近 0.8 GB，再加 API 进程和系统余量，1 GB 服务器有被打满的风险。抖音
现已转为协议路径，正常情况下不会占用浏览器槽位。当前缓存只复用相同接口和相同参数，
不跨互动量/评论接口减少请求数。

## 仍存在的数据缺口

- 公众号：作者关闭评论时不存在可采集内容；任意文章的阅读/点赞和未预载精选评论依赖手机
  微信文章短时会话。服务器仅凭 URL 和 IP 不能替代这个权限。自有公众号可另接官方统计
  API，第三方文章只能使用调用方自己的本地微信会话快照。
- 小红书：新游客会话以每 4 秒一次请求评论首屏时成功 95/100；互动量混合阶段成功
  29/100。后续页需要调用方自己的有效 Cookie 与 URL 对应 `xsec_token`。当前便宜代理
  即使对齐 GeoIP/时区也不能稳定解除验证码，IP 池不能替代账号会话。
- 微博：匿名接口前两页已覆盖，深页可能返回 `ok=-100`；项目会复用本地登录 Profile 的
  Cookie、XSRF 和 `max_id_type`，有会话时继续热门流分页。
- 快手：当前 API 返回一级评论及每条的子回复数量；子回复有单独 `comment/sublist` 协议，
  但把它混入“每页 20 条一级评论”会破坏现有页码语义，因此未伪装成同一评论页。
- B 站直播：公开接口只能读取最近弹幕窗口，URL 无法回溯已经过去的历史弹幕。若业务需要
  未来全量，需增加常驻 WebSocket 录制器和数据库，而不是对历史 URL 重试。
- 头条、好看：没有在页面公开的收藏/分享等数字保持 `null`；不从推荐流或模糊文案猜值。

这些缺口不是增加 IP 或并发就能解决。当前策略是先返回所有可验证字段，再用
`coverage/reason` 明确指出权限、时间窗口或公开字段边界，避免把空数据当成功。
