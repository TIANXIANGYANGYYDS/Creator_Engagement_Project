# 成本、容量与保护策略

验证日期：2026-08-24。本文只描述运行成本和服务保护；每个平台的字段、分页和会话边界见
`PLATFORM_FLOWS.md` 与 `PROTOCOL_MATRIX.md`。

当前对外能力为九个平台 18 个独立业务项。下方“历史 16 项”保留新增微信视频号前的同 URL
基线，不能代表当前平台数量；视频号和公众号当前路径另列专项实测。

## 请求次数和 IP 次数不是同一口径

互动量和评论仍是两个独立的原子业务操作；批量接口只负责统一调度这些操作：

```text
POST /api/v1/collect
GET /api/v1/interactions?url=...&media_name=...
GET /api/v1/comments?url=...&media_name=...&page=1
```

批量 `items` 中每一项仍明确选择互动量或评论。两个原子操作独立执行、独立缓存；只有完全
相同的接口参数才会合并并发重复任务，并复用 120 秒结果。批量响应的 `cost_yuan` 只核算
该批次触发代理池实际新增的 IP，复用已有 IP、直连和缓存命中均不增加该值。

一次业务接口内部可能包含页面预热、访客状态初始化和数据接口等多个 HTTP 请求。它们可以
共用一个代理租约，但仍应分别计入上游请求数量。反过来，一个代理 IP 在约 170 秒可用期内
也可以连续承载多次业务请求，所以不能把“一个 IP”直接等同于“一次请求”。

评论接口只读取一级评论正文，不会为每条评论继续扇出回复请求。响应中的 `replies` 只是
平台已返回的回复数量，因此不会额外增加 HTTP 请求、IP 成本或浏览器负载。

### 微信公众号当前授权路径

公众号与视频号不是同一平台。任意第三方公众号文章仍遵守页面/短时文章会话边界；自有
公众号现在可配置 AppID/AppSecret 或已有 access token，使用当前官方接口：

| 独立业务接口 | 实际上游流程 | 采购 IP 口径 | 当前验证 |
|---|---|---|---|
| 自有公众号互动量 | 1 GET 文章元数据 + 1 POST `getarticletotaldetail`；`stable_token` 每约 2 小时摊销一次 | 默认 `direct/prefer` 下官方 POST 直连；文章 GET 是否用代理取决于部署；显式 `required` 仍使用代理 | mock 协议/字段匹配通过；缺用户凭据，未计入真实成功率或单价 |
| 自有公众号评论 | 1 GET 文章元数据 + 1 POST `comment/list`；token 复用 | 同上 | mock 分页通过；只适用于凭据所属公众号及已开通留言的文章 |

官方凭据路径不是付费数据供应商，但需要公众号自身授权、接口权限和服务器 IP 白名单。
没有用户实测凭据时不能把它写成“直连百测成功”或给出虚构 P50；任意第三方文章也不能
套用这一成本。

### 微信公众号 Cookie-only（任意公开文章）

当前生产主路径不启动微信客户端或浏览器。调用方把完整 Cookie Header 写入
`.local/env/.env` 的 `WECHAT_ARTICLE_COOKIE`，代码从 Cookie、文章 URL 和
`window.cgiDataNew` 合并短时参数：

| 独立业务接口 | 实际上游流程 | 采购 IP 口径 | 当前验证 |
|---|---|---|---|
| 公众号互动量 | 1 GET 文章 HTML；无统计时再 1 POST `getappmsgext` | 一个业务调用只租 1 个 IP；新 IP 上限成本 ¥0.00084，3 分钟内成功复用的新增成本 ¥0 | 165 项自动化通过；无 Cookie 真实 5 次均 `unsupported`，P50 1.611 秒；待用户 Cookie 实测成功率 |
| 公众号评论第 1 页 | 1 GET 文章 HTML；无预载时再 1 GET `appmsg_comment` | 同一 Cookie/IP 租约完成两个 GET；不是两个 IP | 无 Cookie 真实 5 次均 `unsupported`，P50 0.896 秒；Cookie buffer 分页 contract 通过 |
| 公众号评论第 N 页 | 1 GET HTML + 最多 N 个评论 GET，逐页读取 `buffer/continue_flag` | 整个翻页业务调用仍只租 1 个 IP，但微信上游请求数为 N+1 | 自动化验证第 2 页游标转换、去重边界和结束页；待真实 Cookie 深分页 |

Cookie 本身没有采购费用，但不是匿名权限。公开实现所需能力字段为
`uin/key/pass_ticket/appmsg_token/cookie`；常见 Cookie 还含 `wap_sid2`。`ret=-3/no session`
会直接返回 `unsupported`，不会靠轮换 IP 重试；HTTP Verify/验证码才会淘汰 IP。
互动和评论来自不同微信上游响应，不能合并成“一次请求成本”。

### 微信公众号本地会话桥（旧兼容模块）

官方路径不能覆盖第三方公众号后，项目已实现免费 sidecar。用户电脑中的微信客户端打开
同一公众号一篇文章后，短时会话按 `__biz` 在内存保留约 25 分钟：

| 独立业务接口 | 实际上游流程 | 采购 IP 口径 | 当前验证 |
|---|---|---|---|
| 公众号互动量 | 1 GET 凭据化文章页；页面不下发计数时再 1 POST `getappmsgext` | 微信桌面电脑直连，不调用 51 IP，采购 IP 成本 ¥0 | 自动化模拟响应通过；待用户本地微信会话做真实百测 |
| 公众号评论第 N 页 | 1 个或多个 GET `appmsg_comment`，按 `buffer` 遍历到所需页 | 同上 | 页码转换、精选评论标记、会话失效处理通过；待真实百测 |

该模块按用户当前风险要求不作为生产验收路径。它不消耗采购 IP，但不是零资源：需要一台已登录微信桌面端，微信 4.x 的 WebView 通常会
占用数百 MB；会话桥和 mitmproxy 本身远低于浏览器集群。互动和评论来自不同微信上游响应，
不能合并成“一次请求成本”。打开文章时已观察到的响应可由桥直接复用，减少后续请求。

### 微信视频号 100 + 100 次专项

使用 3 条有效公开分享链接轮换，业务缓存、代理和浏览器均关闭。互动量和评论接口分别调用
100 次；100 个任务同时进入企业限流队列，平台并发 2、每 0.2 秒启动一个：

| 独立业务接口 | 实际上游流程 | 结果 | 端到端排队 P50/P95 | 新增 IP | IP 成本 |
|---|---|---|---:|---:|---:|
| 视频号互动量 | 1 POST `get_feed_info` | 100/100 返回点赞、评论总数、转发、收藏显示值 | 12.392 / 21.663s | 0 | ¥0 |
| 视频号评论第 1 页（匿名降级） | 1 POST `get_feed_info` | 评论总数 100/100；正文 0/100 | 11.716 / 22.348s | 0 | ¥0 |

两个业务接口都只有一个上游 POST；本次直连实测的实际采购 IP 成本为零，默认 `prefer`
也会绕过代理，只有显式 `required` 才按运维要求使用代理。这里的高
P50/P95 主要是 100 请求同时入队后的保护性排队，整批最大完成时间分别为 22.990 秒和

P50/P95/最大为 0.063/0.088/0.213 秒。评论响应只有总数，不满足“评论内容”需求，成本单
仍分两行并标为不可用，不能因请求成功就记成评论正文成功。

### 微信视频号授权客户端正文路径

配置 `WECHAT_CHANNELS_BRIDGE_URL` 后，评论成功路径不再先调用公开预览，而是由 Windows
侧车执行 1 次分享详情、必要时 1 次精确搜索，以及每页 1 次 `finderGetCommentList`。这些
请求从 Windows 微信客户端直连，不租用 51 代理，因此采购 IP 成本为 ¥0；但终端、微信
WebView 和常驻侧车并非零资源。

| 独立业务接口 | 实际上游流程 | 采购 IP | 当前验证 |
|---|---|---:|---|
| 视频号互动量 | 主服务器 1 POST `get_feed_info` | 0 / ¥0 | 100/100 真实公开链接有数据 |
| 视频号评论第 1 页 | 侧车 1 profile + 0/1 search + 1 comment/list | 0 / ¥0 | 目标匹配、正文映射、鉴权和分页 contract 通过；缺授权终端，未做真实百测 |
| 视频号评论第 N 页 | 侧车 1 profile + 0/1 search + N 次 comment/list | 0 / ¥0 | `lastBuffer` 顺序转换测试通过；待授权终端实测吞吐 |

侧车不可用时评论接口才额外执行 1 POST `get_feed_info`，返回准确总数与 `unsupported`。
建议单终端 0.5–1 秒间隔、单并发；因此保守容量约 1–2 页/秒/终端。真实延时和 RSS 必须在
实际 Windows 微信版本上压测后再写入价格单，当前不能用 mock 延时冒充生产数据。

## 默认保护参数

| 参数 | 默认值 | 作用 |
|---|---:|---|
| `COLLECTION_MAX_CONCURRENCY` | 8 | 全服务最多 8 个上游采集任务 |
| `BROWSER_MAX_CONCURRENCY` | 3 | 最多 3 个独立 Profile 的 Camoufox 槽位 |
| `BROWSER_MAX_ATTEMPTS` | 3 | 空字段、挑战或执行失败时最多使用 3 个浏览器出口 |
| `BROWSER_GEOIP_ENABLED` | `false` | 关闭非必要第三方 GeoIP 探测，避免代理误淘汰 |
| `PROXY_POOL_SIZE` | 8 | 维护 8 个代理槽位，使坏 IP 淘汰/补池不阻塞全部请求 |
| `PROXY_MAX_CONCURRENCY` | 1 | 每个 IP 只承载 1 个同时在途业务流程，降低同出口风控 |
| `RELIABILITY_MODE` | `enterprise` | 启用语义失败换 IP、协议重试和平台级节奏 |
| `PROTOCOL_MAX_ATTEMPTS` | 3 | 失败、阻断或可重试缺字段最多尝试 3 次 |
| `TOUTIAO_PROTOCOL_MAX_ATTEMPTS` | 1 | 头条互动 SSR 只探测一次，随后进入既有兜底链路 |
| `DOUYIN_PROTOCOL_MAX_ATTEMPTS` | 3 | 抖音临时失败时最多使用 3 个独立代理租约和 HTTP 会话 |
| `DOUYIN_MAX_CONCURRENCY` | 4 | 抖音平台并发；2/4/6 档真实请求对照后的稳定档位 |
| `PROTOCOL_RETRY_BASE_SECONDS` | 1 | 通用指数退避基数；小红书互动换 IP 不等待，评论仍保留 4 秒节奏 |
| `ENGAGEMENT_CACHE_TTL_SECONDS` | 120 | 相同接口和相同参数的结果复用 2 分钟 |
| `ENGAGEMENT_FAILURE_CACHE_TTL_SECONDS` | 15 | 临时失败只短缓存 15 秒，避免可恢复故障长时间固化 |
| `ENGAGEMENT_CACHE_MAX_ENTRIES` | 1000 | LRU 上限，防止缓存无限增长 |
| `ENGAGEMENT_CACHE_MAX_BYTES` | 67108864 | LRU 总量最多 64 MiB，避免少量大评论页占满内存 |
| `JOB_MAX_ITEMS` | 5000 | 单个异步任务的项目数硬上限 |
| `JOB_RESULT_MAX_BYTES` | 8388608 | 单条异步结果最多 8 MiB，低于 MongoDB 单文档上限 |
| `JOB_RESULT_TTL_SECONDS` | 86400 | MongoDB 任务和逐条结果结束后保留 24 小时 |

协议请求全局允许 8 并发；企业模式下头条并发 3、抖音并发 4，小红书、快手、公众号各自单并发，视频号并发 2。
小红书互动和评论分别按 1 秒、4 秒启动，快手和公众号均为 0.5 秒，视频号为 0.2 秒。平台限流等待发生在全局信号量之外，
不会用一个慢平台占满全部槽位。
浏览器并发槽使用独立 Profile，避免同目录锁退化为串行；不应通过增加 Uvicorn worker
进程绕过限制，因为每个进程会重复创建缓存、浏览器槽位和代理池。历史任务结果直接从 MongoDB
分页读取；Python 进程只保留运行中任务，不在启动时恢复全部结果到内存。

### 2026-08-30 真实 2820 条基线与抖音并发定标

从外部历史任务原样恢复 2820 个互动项（抖音 1694、微博 1126），关闭业务缓存、单项/整批
截止时间和平台熔断，强制所有目标请求经过 8 槽代理池。完整基线全部落库，2642 条成功，178 条
失败均为作品已删除、仅自己可见或无查看权限等确定性状态；任务级无中断。墙钟时间
1072.45 秒，新增 60 个代理，成本 0.0504 元。只有 33 个内容触发协议重试，其中 5 个需要第 3
次尝试，证明 3 次尝试有实际价值，但不需要继续放大。

随后从同一批结果中等距固定抽取 400 条（抖音 240、微博 160），每次重启后关闭缓存并使用完全
相同的 URL 做 2/4/6 档对照：

| 抖音并发 | 成功 / 失败 | 墙钟时间 | 新增代理 / 成本 | 结论 |
|---:|---:|---:|---:|---|
| 2 | 371 / 29 | 132.16s | 9 / 0.00756 元 | 稳定但平台队列偏长 |
| 4 | 371 / 29 | 71.00s | 8 / 0.00672 元 | 结果不变，耗时下降 46.3% |
| 6 | 370 / 30 | 183.52s | 17 / 0.01428 元 | 坏代理占满槽位，增加 2 个网络型失败 |

因此生产值选 4，而不是追求理论最大并发。正式网络超时恢复为 20 秒，单项/整批上限分别为
90/1800 秒，连续临时失败阈值为 24、冷却 20 秒；熔断改为等待冷却后真实探测，不会直接把
排队项目批量标记失败。临时失败缓存从 120 秒缩短为 15 秒，允许外部重试快速重新触发真实采集；
删除、无权限等确定性不可用状态仍按正常 120 秒缓存，避免无效重复请求消耗代理。

清空内存缓存并以这套正式参数重新执行全部 2820 条后，结果仍为 2642 成功、178 个确定性失败，
没有单项超时、网络型终态失败或熔断事件。墙钟时间为 627.18 秒，较宽松基线下降 41.5%；吞吐从

## 51 代理成本

用户给出的价格是 100000 个 IP 共 84 元，因此单个 IP 为：

```text
84 / 100000 = 0.00084 元/IP
```

正确核算公式是：

```text
代理总成本 = 实际新增 IP 数量 × 0.00084 元
平均业务请求成本 = 代理总成本 ÷ 成功业务请求数
平均上游请求成本 = 代理总成本 ÷ 成功上游 HTTP 请求数
直连且没有调用代理池：IP 采购成本 = 0 元
```

### 本轮代理实际消耗

上述 16 个独立业务接口以单 IP、单并发连续执行，实际结果为：

```text
总用时                 94.651 秒
业务接口调用           16 次
取得有效结果           14 次（小红书两项未取到）
代理租约               19 次
代理池 API             1 次
实际新增 IP            1 个
失败淘汰/过期换 IP      0 个
实际 IP 成本            1 × 0.00084 = 0.00084 元
按全部调用摊销          0.00084 / 16 = 0.0000525 元/次
按有效结果摊销          0.00084 / 14 = 0.00006 元/次
```

这不是固定单价。该 IP 恰好在 94.651 秒内承载了 19 次租约且未失效；改变调用顺序、平台
风控、代理质量或运行时长后，摊销会变化。直连轮没有调用代理池，实际 IP 采购成本为 0 元。

51 代理标称有效期 3 分钟，代理池提前 10 秒停止分配，所以每批 IP 可用约 170 秒。默认池
大小为 4；在四个槽位持续满负载、没有失败淘汰的理论上限下：

```text
每小时 IP = 4 × 3600 / 170 ≈ 84.71
每小时费用 = 84.71 × 0.00084 ≈ 0.0712 元
100000 IP 可连续支撑 ≈ 1181 小时 ≈ 49.2 天
```

这是代理池四槽全占用上限；生产平台级单并发通常不会同时占满四槽。代理池不会在无请求时
主动刷新，因此低流量的实际消耗更低。按已读取的 407 URL 文件平台
分布，并把每个 URL 的互动量和评论各请求一次，以本轮各平台代理实测时间线性估算：

```text
共 814 个业务接口调用
实测速度线性估算        约 79.1 分钟
按 25% 余量规划         约 107.3 分钟
无失败时预计新增 IP      约 28–38 个
预计 IP 成本             0.02352–0.03192 元
```

这是上一轮根据 407 条文件做的线性预测。随后已经完成更大的真实全量，以下实账取代该预测
作为当前容量基线。

## 仍存在的数据缺口

- 公众号：匿名 `show_comment=0` 不能证明作者关闭评论；任意文章的阅读/点赞和未预载精选
  评论依赖完整文章 Cookie。服务器仅凭 URL 和 IP 不能替代这个权限。自有公众号已接当前官方统计
  和留言 API，第三方文章只能使用调用方自己的本地微信会话快照。
- 微信视频号：公开分享互动量和评论总数 100/100，匿名评论正文 0/100。授权客户端正文
  适配器已实现，需要 objectId、objectNonceId 和 lastBuffer；IP 池或匿名浏览器不能替代
  该会话，真实成功率与负载待 Windows 授权终端验收。
- 小红书：互动量对当前有效 token URL 为匿名 SSR 100/100；缺少或已经失效的
  `xsec_token` 不能仅凭 note ID 补回。评论低频首屏为 20/20；当前已接入专用 Cookie Secret，
  仍需要调用方自己的有效 `a1/web_session` 与 URL token，便宜代理不能替代评论会话。
- 微博：匿名接口前两页已覆盖，深页可能返回 `ok=-100`；项目会复用本地登录 Profile 的
  Cookie、XSRF 和 `max_id_type`，有会话时继续热门流分页。
- 快手：企业协议首屏互动/评论均为 398/398 有数据；其中 34 条作品详情已不可用，只能返回
  评论数。API 只返回一级评论正文；平台随一级评论返回的回复数量作为数字保留，不继续请求
  回复正文。
- B 站 Opus：页面通常公开赞、评、转、藏和投币，但未公开阅读数时 `views=null`；项目不从
  其他口径推算。直播 URL 属于明确的非业务输入，会在请求上游前拒绝。
- 头条、好看：没有在页面公开的收藏/分享等数字保持 `null`；不从推荐流或模糊文案猜值。

这些缺口不是增加 IP 或并发就能解决。当前策略是先返回所有可验证字段，再用
`coverage/reason` 明确指出权限、时间窗口或公开字段边界，避免把空数据当成功。
