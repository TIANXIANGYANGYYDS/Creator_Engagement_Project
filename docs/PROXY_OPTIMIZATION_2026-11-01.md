# 代理池隔离优化实验（2026-11-01）

当前结论：**先采用任务寿命准入、按需小批补池和失败分类；本轮证据不支持把所有 IP 统一提高到 20 并发。** 实验实现由 `PROXY_LEASE_OPTIMIZATION_ENABLED` 控制，默认关闭。尚未部署或重启线上服务，也没有修改生产环境变量。2 Mbps 是用户确认的暂定实验假设，尚未核实供应商实际限速。

18:22 补充：上述为候选方向，不是全量上线建议。当天生产请求复核仍发现 18:21 确认外部来源的微博评论 502、头条评论 504/502、6 项 B 站动态超时及两次重试后恢复的抖音临期事件。候选代码没有被线上加载；短批对照不能保证真实大批量负载无退化，开关继续关闭。详细口径与原因见 [当天生产请求复核](REQUEST_REVIEW_2026-11-01.md)。

## 原调用流程与问题

业务缓存/合并请求 → 平台限速与全局并发槽位 → 每次协议尝试建立懒加载租约 → 代理池选择可用 IP → 同一尝试中的页面、签名/访客与数据请求复用该 IP → 归还；必要时从新的尝试边界重试。浏览器兜底使用相同供应商池、独立浏览器并发控制。作者任务也使用共享 HTTP 客户端和代理池。小红书现有显式独立出口与会话例外保持原状。

原池只判断 IP 是否到本地截止点，不判断剩余寿命能否覆盖下一段工作。供应商租期 180 秒，旧逻辑在返回入池时计算约 170 秒可用期；首次缺少可用槽位会补满 8 个。优先选择负载低、较早到期的 IP。抖音先拿 IP，再等访客初始化锁，直到初始化完成才验证剩余寿命，所以可能把临期 IP 的最后十几秒花在初始化上。

原实现把不少业务不可用结果与连接失败统一淘汰代理；在低流量或空页场景下，补满池和过度淘汰都会增加采购量。

## 实验实现

- 分配时同时检查剩余寿命、租约并发、独占占用及冷却状态。短任务仍可使用不能承接长任务的旧 IP。
- 初始/后续按需每批最多提取 2 个，容量上限仍可保持 8；不运行额外后台采购循环。实际采购仍受原供应商限流器保护。
- 保守从提取调用开始计时，扣除原有 10 秒安全余量，再分散提前 0～5 秒停止分配，避免把提取等待时间额外算进租期。
- 池满但没有符合条件的槽位时，只替换一个空闲、不符合条件的 IP；不打断其他任务正在使用的 IP。供应商重复返回被替换 IP 时不会立刻赋予全新寿命，无可用端点则有限失败，禁止直连。
- 传输异常先全局冷却 15 秒；累计错误分数达到 3 后排空。成功且已过冷却期可减一分。平台拒绝仅对该平台冷却 30 秒；解析/业务不可用、取消、寿命不足不直接降低全局 IP 健康度。池满且需要可用容量时，冷却中的空闲 IP 仍可能被替换，不能将“未全局判坏”理解成永不采购。
- 抖音等待初始化锁后再次检查 IP；冷启动前提高寿命要求，访客 Cookie 缓存也必须至少留出下一次请求的预算。尚未使用的租约允许重选；已经发出请求或启动浏览器后，寿命不足必须退出当前尝试，从会话边界重试，不能带着旧身份悄悄换 IP。
- 实验模式下，各协议操作隔离 Cookie jar；抖音、作者采集和浏览器操作独占该 IP 租约，避免与普通协议任务争用带宽。原浏览器兜底保留。
- 单 IP 租约并发允许设置 1～20，**租约数不是实际 TCP 连接数**。浏览器还会请求多个资源，不能用一个浏览器租约证明供应商连接并发小于 20。

`ineligible_replacements` 同时统计寿命不足和冷却造成的空闲替换；早期实验 JSON 中该字段名为 `budget_replacements`。`lifetime_rejections` 是筛选检查次数，不是独立 IP 数。冷却是依据错误类别采取的保守策略，不等于已经证明故障由出口 IP 导致。

## 历史耗时与初始寿命预算

读取已有 6,755 条历史批任务结果，没有调用线上采集接口来生成这组历史。下表为对应媒体成功项的业务耗时，**包含排队和重试**，不是单次网络耗时，也不是全部来自评论请求。失败样本单独保存，未混入成功 P95；较小样本不足以支持精细阈值。

| 历史媒体分组 | 成功样本 | P50 | P95 |
|---|---:|---:|---:|
| 抖音 | 2,426 | 2.104 s | 10.162 s |
| 微博 | 1,224 | 0.688 s | 29.664 s |
| 哔哩哔哩 | 19 | 22.746 s | 58.250 s |
| 快手 | 17 | 48.199 s | 88.886 s |
| 今日头条 | 440 | 2.821 s | 25.684 s |
| 搜狐号 | 339 | 3.161 s | 52.791 s |

结合现有 HTTP 20 秒超时、浏览器初始化流程和上述粗粒度历史，先使用以下**实验准入预算**，不直接把业务 P95 复制成单次超时：

| 工作类型 | 分配时至少剩余可用寿命 | 是否独占 IP 租约 |
|---|---:|---|
| 普通协议操作 | 35 s | 否 |
| 微博协议操作 | 40 s | 否 |
| B 站 / 快手 / 微信协议操作 | 60 s | 否 |
| 抖音已有可复用访客 | 25 s | 是 |
| 抖音冷启动访客 | 70 s | 是 |
| 作者任务 | 60 s；启动浏览器前提高至 70 s | 是 |
| 通用浏览器兜底 | 90 s | 是 |

每个后续 HTTP 请求前再检查“该客户端超时 + 5 秒”，队列等待不能绕过此检查。作者分页保留现有轮换规则。以上只是当前一次尝试/下一段工作的预算，不保证长分页任务、多个串行请求、供应商实际提前失效都能被固定阈值覆盖。后续需要按平台、操作、冷/热启动分别采集租约占用时长，再调整阈值；本轮没有伪造精细历史。

## 实网对照：采购量下降，可用率没有提高

独立子进程运行旧提交 `cecdffc` 的源码快照与候选代码；不创建 API/任务 worker，不访问 MongoDB，不调用告警发送，不连接小红书会话。使用同一批历史 URL，各选 16 个来源各一篇互动量，全局并发 4、每来源并发 1、每 IP 并发 1、池容量 8。关闭业务缓存与通用浏览器兜底以控制变量；抖音访客专用浏览器只在后面的评论对照使用。运行顺序为旧 A、新 A、新 B、旧 B，所有租约均归还。

| 轮次 | 可用项 | 整批耗时 | 新增 IP | 供应商调用次数 |
|---|---:|---:|---:|---:|
| 旧 A | 15/16 | 16.169 s | 8 | 1 |
| 新 A | 16/16 | 8.455 s | 6 | 3 |
| 新 B | 15/16 | 9.530 s | 6 | 3 |
| 旧 B | 16/16 | 7.822 s | 8 | 1 |

两轮合计都是 **31/32** 可用；新增 IP **16 → 12（减少 25%）**。批次平均耗时 **11.995 → 8.993 秒**，但旧 B 比两轮候选都快，样本小且出口不同，不能据此宣称稳定提速或成功率提升。新策略用更多次供应商调用换取较少的提取 IP，需要继续监控供应商 API 限流与采购延迟。全部为冷池短批次，不能外推为持续高负载下必然节约 25%。

## 单 IP 并发实验

实网保持池容量 1、全局并发 4、同一组 16 个来源，只改变每 IP 并发。连接失败或冷却可能触发替换，因此“容量 1”不表示整批始终使用同一个出口。不同轮次的出口不同，无法将波动单独归因于并发或带宽。

| 每 IP 并发 | 首轮可用 / 耗时 / 新增 IP | 反向复测可用 / 耗时 / 新增 IP |
|---|---|---|
| 1 | 16/16 · 11.272 s · 1 | 16/16 · 18.758 s · 1 |
| 2 | 15/16 · 18.390 s · 5 | 15/16 · 53.997 s · 5 |
| 4 | 15/16 · 15.755 s · 4 | 11/16 · 45.636 s · 9 |

首轮按 1 → 2 → 4，复测按 4 → 2 → 1。两轮合计并发 1 为 **32/32** 可用、提取 2 个 IP；并发 2 为 **30/32**、提取 10 个；并发 4 为 **26/32**、提取 13 个。高并发组出现更多连接超时/TLS/连接错误，当前没有提高线上并发的依据；出口差异、时间变化与小样本限制仍然成立，不能断言是供应商带宽或风控所致。

### 本地可控 2 Mbps 限速

本地模拟 HTTP 代理共用 250,000 B/s 响应体带宽，每次响应前固定等待 250 ms；通过**真实项目 curl 客户端和代理池**发送 20 个任务，分别测试 16 KiB、128 KiB 响应体及 1/2/4/8/20 并发。没有请求外部平台，没有修改主机网卡或线上限速。

| 单 IP 并发 | 16 KiB × 20 整批耗时 | 128 KiB × 20 整批耗时 | 128 KiB 取得租约后 P95 |
|---|---:|---:|---:|
| 1 | 6.402 s | 16.022 s | 0.801 s |
| 2 | 3.614 s | 13.245 s | 1.338 s |
| 4 | 2.221 s | 11.755 s | 2.434 s |
| 8 | 1.766 s | 11.429 s | 4.633 s |
| 20 | 1.632 s | 11.284 s | 11.264 s |

128 KiB 样本的总响应体为 2.5 MiB，理论传输下限约 10.49 秒。4 → 20 并发只再缩短约 **4%**，取得租约后的单任务 P95 却约为 **4.6 倍**。注意该 P95 不含池内排队；整批/从提交开始的耗时仍有下降，不能把这个实验说成“高并发必然让用户等待更久”。16 KiB 小包等待占比较高，增加并发收益更明显。

这证明带宽需求应进入调参依据，并不证明真实代理就是 2 Mbps。实网互动批次实际下载的 HTTP 响应体约 0.61～0.65 MB，其中不含浏览器资源、TLS/IP 额外流量及失败请求未返回的流量，因此也不能用这组记录认定链路已打满。暂不加入会重复限速的固定令牌桶，不直接将全平台提升至 20；先保留 1，后续将确有收益的轻量任务单独灰度 2～4，浏览器保持独占。

## 评论与抖音验证

串行比较 8 个控制项，旧版提取 8 个 IP、用时 35.701 秒，候选提取 2 个 IP、用时 17.610 秒。两版均为 6 个可用首屏样本，另有 1 个确定不可见样本和 1 个超出已有评论的空页；不能按“6/8”简单计算故障率，也不能将非空页视作评论全集。所有结果核对了目标 ID、业务状态、一级正文与零/未知计数，未以 HTTP 200 验收。

| 样本 | 旧版 | 候选 | 判断 |
|---|---|---|---|
| 微博非空评论 | 4 条，total=4 | 3 条，total=4 | 目标一致；匿名折叠/返回有波动，均 partial，不证明全集 |
| 微博明确零评论 | 0 / total=0 | 0 / total=0 | 一致 |
| B 站公开视频 | 2 条，total=2 | 2 条，total=2 | 一致 |
| B 站公开 Opus 零评论 | 0 / total=0 | 0 / total=0 | 一致 |
| B 站仅 UP 主可见稿件 | unsupported，62012，1 次尝试 | 同左 | 不把未知数值填零，不反复换 IP |
| 澎湃第 1 页 | 4 条，total=4 | 4 条，total=4 | 一致 |
| 澎湃第 2 页 | 0 条，total=4，无下一页，3 次尝试 | 同左 | 既有空页重试仍在，候选不再据此全局判坏 IP |
| 抖音已知零评论样本 | 0 / total=0，3.867 s | 0 / total=0，4.262 s | 冷启动与协议链路均可用，未证明抖音提速 |

另外使用可控时钟复现“IP 剩余 15 秒，初始化消耗 20 秒”：旧策略在初始化后报临期，候选在初始化前换用满足预算的 IP。同样测试了排队期间过期、访客 Cookie 临期、已开始流程禁止中途换 IP、独占与 20 租约共享互斥、供应商重复旧 IP、取消与失败归还。

## 验证、运行边界与复现

- 全量测试：**935 passed，22 skipped**。跳过的是已有显式 opt-in 集成测试，没有为了跑测试接入生产 MongoDB。
- 线上 PID、源码目录、运行源码散列与 `.local/env/.env` 散列均未改变；只读健康检查返回 `ok`。
- 原始历史、实网结果、控制项结果、限速实验与脚本在 `.local/analysis/proxy-optimization-20261101/`，不提交原始会话或供应商配置。
- 主要实现：`app/crawlers/proxy_policy.py`、`proxy_provider.py`、`http_client.py`，以及抖音、浏览器、作者租约接入；回归用例在 `tests/test_proxy_optimization.py`。
- 本地回归：`python -m pytest -q tests/test_proxy_optimization.py`。
- 实验参数只传给独立进程的 `Settings`：`proxy_lease_optimization_enabled=True`、`proxy_refill_batch_size=2`；生产默认仍为 `false`。`.env.example` 只记录默认值与开关说明。
